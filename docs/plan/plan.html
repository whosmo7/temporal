Project plan

What would responsibility mean if the people affected by your choices could never reward you?

A browser-based, async-multiplayer farming game for OxHack (48h, team of 3–4). Each player governs a small seeded world for one timed turn (one generation). They inherit what earlier players left: resources, structures, consequences already in motion, and a shared journal. Some actions pay off right away. Others only mature after the player has left. When a world reaches its final generation, a replay shows what each player actually caused.

This folder is the plan. It is split by area so each person can own a section. It is not a build-everything-in-one-go spec. Each doc has:

  • Decisions: what the team has already chosen (from the planning Q&A)
  • Spec: how it should work
  • Tasks: checklists, roughly in dependency order
  • Acceptance: how you know the section is done
  • Open questions: things still to decide. Nothing here has been assumed.

Values marked placeholder are suggested starting numbers for the game designer to tune. They are not decisions.

01

Game Design: Resources, Actions, Rules

Owner: Game design (with Engine)
Depends on: nothing. This feeds 02-engine (as config.ts) and 04/05 (what to show).

Decisions (locked)

  • Resources: Food, Water, Labour (= player stamina).
  • Eight actions: Harvest, Plant Crops, Plant Orchard, Repair Reservoir, Dig Well, Fish/Hunt, Maintain, Fast Track.
  • Unlimited actions within a configurable turn length. Stamina and resources are the real limits.
  • End-of-turn upkeep (food + water). Missing it = weakened start for the successor.
  • Decay (food rots, water stagnates) + infrastructure wear (structures degrade unless maintained).
  • Partly hidden delayed effects: players see growth or decay visually, never the exact numbers or due dates.
  • Seeded events only (e.g. a drought). No borrowing, no score.
  • The reservoir dilemma is tuned in on purpose.
  • Biome (Forest / Island) gives small modifiers only.

Design goal: avoid a morality game

Every action has to be something a reasonable person would choose. There is no "good" button. The tension comes from:

  1. Your own survival vs. the future. Upkeep is real, and failing it hurts your successor.
  2. Cashing in vs. preserving. Fast Track lets you take a predecessor's gift early, at double cost.
  3. Quick fixes with a tail. The well gives water now, but it obliges every later player to maintain it.
  4. Commons depletion. Fish/Hunt stock is shared across generations and recovers slowly.
  5. Invisible protection. Repairing the reservoir does nothing you can see in your own turn. It only matters when the seeded drought arrives.

Self-check for every balance change: could a thoughtful player defend each option?

Core loop (one generation)

  1. Inherit. Spawn in the world. Resources, structures and graveyard are as the previous player left them, after decay, wear, due effects and events have been applied. The journal is on a lectern and openable any time.
  2. Act. The timer runs and day turns to night. Walk to plots and act. Each action costs stamina (and sometimes water or food).
  3. Freeze. The timer hits 0, the world freezes, and input locks.
  4. Journal. Write or draw your page. Earlier pages are read-only.
  5. Cost summary. Shows only what was realised this turn. Pending benefits are left out.
  6. Upkeep check. Food/water are deducted. A shortfall marks the successor as weakened.
  7. Gravestone. Your stone is placed in the graveyard. The turn is committed.
  8. Between turns (engine). Decay, wear, due effects, seeded events and wild stock regrowth are applied for the next generation.

Open: should upkeep be checked before the journal, so the player knows whether they've failed while writing? The current order has the cost summary after the journal.

Why the reservoir dilemma works (with placeholder numbers)

  • Starting stamina 100. Upkeep 10 food + 10 water.
  • Repair = 55 stamina. That leaves 45, enough for about 4 Fish/Hunt (+20 food) or 2 crop cycles.
  • If the player inherits low food, repairing means risking upkeep. Skipping it means the seeded drought hits a successor.
  • Tuning target: a player who inherits a "medium" world can either repair or comfortably feed themselves, not both.

Fast Track details

  • Shows every pending effect in the world, including other players' (e.g. "Orchard planted, Gen 1").
  • Cost = 2× the original cost (stamina + resources), paid by the current player.
  • Fast-tracking an orchard brings it to fruiting now. Open: does a rushed orchard yield less long-term?
  • It records its own action and its own cause chain, so the replay can say "MO rushed AL's orchard".

02

Simulation Engine: Turn Engine, Action Log, Causality

Owner: Engine/simulation dev
Depends on: 11 (repo scaffold). Consumes 01 config. Consumed by 04, 05, 06, 07.

This is the brief's technical core: an authoritative turn engine and an append-only action log. Every action stores the turn it was committed and the turn it is due. Every state transition records its contributing causes.

Decisions (locked)

  • TypeScript, pure and deterministic: same seed + same action log = same state, every time.
  • Unit-tested with Vitest.
  • Delayed effects are partly hidden from the UI. The engine knows everything. The UI asks for a visual view.
  • Causes are not shown to players during play. They are only used by the replay (06).

Design principles

  1. No React or Pixi imports in src/engine/. It must run in the browser, in Vitest, and in a Supabase Edge Function (Deno).
  2. Pure reducers: (state, input) → { state, transitions }. No Math.random() or Date.now() inside. Use a seeded PRNG and pass time in explicitly.
  3. Append-only log. Never mutate or delete log entries. State can always be rebuilt by replaying the log.
  4. Two time scales: turn (generation index) and t (seconds into the turn, for quick crops and day/night).

Core types (sketch)

type ResourceKey = 'food' | 'water' | 'stamina';
type PlotId = string; // e.g. 'field-1', 'orchard-1', 'reservoir', 'well', 'wild'

interface TimePoint { turn: number; t?: number }        // t = seconds into turn (omit = start of turn)

interface ActionEntry {
  id: string;                 // ulid
  worldId: string;
  actorId: string;            // player profile id
  type: ActionType;           // 'harvest' | 'plantCrops' | ... | 'fastTrack'
  plotId?: PlotId;
  targetEffectId?: string;    // for fastTrack
  committedAt: TimePoint;     // when it was taken
  dueAt: TimePoint;           // when its main effect lands (== committedAt for immediate)
}

interface ScheduledEffect {
  id: string;
  sourceActionId?: string;    // or sourceEventId / rule
  sourceEventId?: string;
  dueAt: TimePoint;
  kind: EffectKind;           // 'orchardMature' | 'reservoirRepaired' | 'cropRipe' | ...
  payload: Record<string, number | string>;
  status: 'pending' | 'resolved' | 'cancelled' | 'fastTracked';
}

type Cause =
  | { kind: 'action'; actionId: string; actorId: string; committedTurn: number }
  | { kind: 'event'; eventId: string }
  | { kind: 'rule'; rule: 'foodRot' | 'waterStagnate' | 'wear' | 'upkeep' | 'regrow' | 'weakened' };

interface Transition {
  id: string;
  at: TimePoint;
  target: { resource: ResourceKey } | { plot: PlotId; field: string };
  before: number | string;
  after: number | string;
  delta?: number;
  causes: Cause[];            // >= 1, always
}

interface WorldState {
  worldId: string; seed: number; biome: 'forest' | 'island';
  turn: number; generationCount: number; turnSeconds: number;
  resources: Record<ResourceKey, number>;
  plots: Record<PlotId, PlotState>;
  pending: ScheduledEffect[];
  wildStock: number;
  weakened: number;           // 0..1 shortfall carried from previous gen
  events: SeededEvent[];      // all events for the world's life, from seed
}

Engine API

createWorld(seed, opts): { state, transitions }                 // Gen 0 starter state (uses 03)
beginTurn(state, actorId): { state, transitions }               // applies between-gen rules for this turn
applyAction(state, action, t): { state, transitions, error? }   // validates cost/target and schedules effects
tick(state, t): { state, transitions }                          // resolves intra-turn due effects (crops)
endTurn(state): { state, transitions, summary }                 // freeze, rot crops, upkeep, realised summary
replay(seed, opts, log): Snapshot[]                             // rebuilds every gen from the log (06)
explain(transitions, filter): CauseSummary                      // aggregates causes for a resource/turn (06)
visibleView(state): VisibleWorld                                // partly hidden, for the UI (no numbers on pending)

Between-generation order (inside beginTurn) — must be fixed and documented

  1. Resolve pending effects due at {turn: n}
  2. Apply seeded events for turn n
  3. Structure wear +1 (unless maintained last turn)
  4. Food rot, water stagnation
  5. Resource income (reservoir, well), reduced by wear and events
  6. Wild stock regrowth
  7. Set starting stamina, applying weakened

Each step emits Transitions with the right causes. A shortage must always trace back to its causes, e.g. "Water −18: drought (event) + reservoir cracked (wear; last maintained by AL in Gen 1)".

Multi-cause transitions

When a value comes from several factors (e.g. reservoir income lowered by both wear and drought), emit one transition with multiple causes, and give each cause its share where possible (causes[i].share?: number) so the replay can say "−12 from drought, −6 from wear".

Authority (async online)

The engine must be authoritative, so the client can't be trusted to write the final world state.

Recommended: the client runs the engine locally for instant feedback and buffers the turn's ActionEntry[]. At end of turn it sends the log to a Supabase Edge Function commit-turn. That function imports the same src/engine package, re-simulates from the stored state, validates the log, appends the action log + transitions + a snapshot, and releases the lock, all in one transaction (see 07).

Fallback if the Edge Function eats too much time: a Postgres RPC that accepts the client-computed result but still only appends. Record this choice as an open question for the engine + backend devs.

Determinism

  • Seeded PRNG (e.g. mulberry32 or sfc32). Each turn's random stream is derived from hash(seed, turn), so the order of actions within a turn doesn't shift later generations' events.
  • IDs: either generated by the engine from (worldId, turn, sequence) or a ULID supplied by the caller. Never random inside the reducer.
  • In-turn time t is passed in by the game loop and clamped to [0, turnSeconds].

03

World Generation: Seeds, Biomes, Plots

Owner: Engine dev (with Art for tile mapping)
Depends on: 02 PRNG. Consumed by 04 (rendering) and 02 (createWorld).

Decisions (locked)

  • Every world comes from a seed. The same seed always gives the same world.
  • ~32×32 tile map, Stardew-style ¾ top-down.
  • A natural boundary encloses the farmable area. Hackathon biomes: Forest (tree ring) and Island (sea).
  • Pre-defined plots for every action (no free placement).
  • Small modifiers per biome (see 01).
  • New worlds start from a seeded starter state.

Spec

Layers

  1. Terrain layer: grass, dirt, sand, water (sea/pond), path.
  2. Boundary layer: dense trees (Forest) or shoreline + sea (Island). It can't be walked through, and it frames the map.
  3. Decoration layer: rocks, bushes, flowers, chosen by the seed. Purely visual and walkable around.
  4. Plot layer: fixed sites placed by the seeded generator inside the boundary, always reachable by path.
  5. Collision grid: derived from layers 1–4 for WASD movement.

Generation outline

rng = prng(seed)
biome = seed-derived or chosen ('forest' | 'island')
mask = radial falloff + noise(seed) → inside/outside boundary
  Forest: outside = tree tiles (2–3 tiles deep)
  Island: outside = sand ring → sea
place plots via rng on a coarse grid inside mask, with min spacing:
  fields ×N, orchard plot ×1, reservoir ×1 (near water/low ground), well site ×1,
  wild spot ×1 (Island: shoreline/pier; Forest: tree edge), lectern ×1 (near spawn), graveyard ×1
carve paths spawn → each plot (BFS on grid) so everything is reachable
scatter decoration avoiding paths/plots

Use a small value-noise or simplex implementation seeded by our PRNG (no global randomness).

Owner: Frontend/UI dev

Decisions (locked)

  • WASD/arrow movement, desktop only.

Row-level security

  • SELECT for everyone (including anon) on worlds, turns, journal_pages, snapshots, actions and transitions of completed worlds. For open worlds, only the lock holder can read the full state (open question: is that worth enforcing?).
  • No UPDATE/DELETE policies on actions, transitions, turns, journal_pages, snapshots (append-only, read-only pages).
  • All writes go through RPC / Edge Function with security definer. Clients never insert directly.

Server operations

claim_world() (Postgres RPC, security definer)

1. If the caller holds an unexpired lock → return that world (resume after refresh).
2. If any world has forced_for = caller and is unlocked → lock and return it (admin force-assign).
3. Expire stale locks: lock_expires_at < now() → clear (turn voided).
4. With probability settings.inherit_ratio, pick a random OPEN, UNLOCKED world
   (SELECT … FOR UPDATE SKIP LOCKED ORDER BY random() LIMIT 1).
   If none / coin says "new" → create a world with a random seed + biome + defaults.
5. Set locked_by = caller, lock_expires_at = now() + turn_seconds + journal_allowance + grace.
6. Return world + latest snapshot (or null for gen 1) + journal pages + gravestones.

SKIP LOCKED + the single-row update guarantees only one player per world.

heartbeat(world_id) (optional)

Extends the lock by a small amount while the client is in the journal/summary phase. It is capped so a player can't hold a world forever. Needed only if the journal-writing time isn't fixed.

commit-turn (Edge Function, recommended; see 02 Authority)

input: world_id, actions[], journal { text, drawing }
1. Verify caller holds the lock and it hasn't expired.
2. Load latest snapshot (or createWorld(seed) for gen 1).
3. engine.beginTurn → apply each action in seq order (validate) → endTurn.
   Reject if any action is invalid.
4. In one transaction:
   insert actions, transitions, snapshot(turn), journal_page, turns row;
   worlds.current_turn += 1; clear lock;
   if current_turn > generation_count → status = 'complete', completed_at = now().
5. Return ok + summary.

Turn voided happens naturally: if the client never calls commit-turn before the lock expires, nothing was ever written.

Fallback if the Edge Function is too slow to build: a commit_turn RPC that accepts client-computed transitions + snapshot and does steps 1 and 4 only.

Client data layer

  • src/api/ wraps supabase-js: signUp, signIn, claimWorld, commitTurn, listCompletedWorlds, getReplay(worldId), admin calls.
  • Env: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY (the anon key is safe in a static bundle when RLS is on).
  • Offline/hot-seat mode (build first, and keep as a demo fallback): the same interface, backed by localStorage, so the game can be developed before the backend exists.
